# Лабораторная работа № 2
## Контейнеризация и оркестрация: Docker и Kubernetes

> [!summary] Цель работы
> Упаковать HTTP- и gRPC-сервис бронирования ресурсов из первой лабораторной работы в Docker-образ, подготовить локальный запуск с PostgreSQL через Docker Compose и развернуть приложение в Minikube. Проверить автоматическое восстановление Pod и обновление Deployment.

## 1. Исходный сервис и окружение

В работе используется сервис бронирования переговорной комнаты и рабочего стола. HTTP- и gRPC-транспорты вызывают один `BookingService`; бизнес-правила лабораторной работы № 1 не менялись. По умолчанию HTTP слушает порт `8080`, gRPC — `9090`.

Основные компоненты:

| Компонент | Назначение |
| --- | --- |
| Go-сервис | Бронирование ресурсов и получение их состояния |
| HTTP | `/health`, `/resources`, `/resources/book` |
| gRPC | `booking.BookingService` и стандартный `grpc.health.v1.Health` |
| PostgreSQL | Инфраструктурная заготовка; сервис устанавливает соединение, но пока не сохраняет в БД бронирования |
| Minikube | Локальный Kubernetes-кластер, версия Kubernetes `v1.37.0` |

При запуске создаются переговорная `id=1` вместимостью 10 человек и стол `id=2`. Состояние пока хранится в памяти процесса и сбрасывается при его перезапуске.

## 2. Multi-stage Docker-сборка

В стадии `builder` используется Go-образ `golang:1.27.1`. Бинарник собирается для Linux со статической линковкой (`CGO_ENABLED=0`). В runtime-стадию переносится только бинарник сервиса; исходный код и Go-тулчейн туда не попадают. Приложение слушает HTTP и gRPC порты, задаваемые переменными окружения `HTTP_PORT` и `GRPC_PORT`.

Для сравнения подготовлен `Dockerfile.single`, который собирает сервис в полноценном Go-образе и оставляет этот базовый образ в итоговом image.

### Сравнение размера

В Docker Desktop на скриншоте сравнения указаны значения **Content Size**:

| Вариант | Content Size | DISK USAGE в снимке |
| --- | ---: | ---: |
| Однослойный `golang`-образ | 386 MB | 1.67 GB |
| Multi-stage runtime | 10.1 MB | 33.7 MB |

По Content Size multi-stage вариант примерно в **38 раз меньше**. Показатель DISK USAGE зависит от локальных слоёв и их совместного использования, поэтому для сравнения итогового содержимого образов приведены значения Content Size.

Меньший образ быстрее передаётся в registry и загружается на узлы кластера, занимает меньше дискового пространства и содержит меньше лишних компонентов. Это сокращает время доставки релиза и объём образа, который нужно хранить и обновлять при масштабировании.

> [!note] О версии runtime-образа
> На скриншотах первоначальная multi-stage сборка использует `gcr.io/distroless/static-debian12:nonroot`. Позже образ `booking-service:v2` собирался уже с `alpine:3.22`. Поэтому размеры `10.1 MB` и `386 MB` относятся именно к сохранённому сравнению на скриншоте, а не являются замером поздней версии на Alpine.

## 3. Docker Compose

`docker-compose.yml` содержит два сервиса: приложение и PostgreSQL. Проверка здоровья PostgreSQL использует `pg_isready`; приложение зависит от Postgres через `depends_on` с условием `service_healthy`. Проверка здоровья приложения обращается к HTTP-эндпоинту `/health`.

Для локального запуска используется команда:

```bash
docker compose up --build --wait
```

Приложение получает адрес БД через `DATABASE_URL` и проверяет соединение перед запуском HTTP- и gRPC-серверов. Реальные запросы бронирования в PostgreSQL пока не выполняются: данные продолжают храниться в памяти.

В ходе проверки Compose оба контейнера перешли в состояние `healthy`; `/health` вернул `200 OK`, gRPC Health/Check — `SERVING`, а в логе сервиса появилась запись об успешном подключении к PostgreSQL.

## 4. Kubernetes-манифесты

Для запуска использовался локальный Minikube с Kubernetes `v1.37.0`. Образ собирался локально и загружался в кластер, Deployment использует `imagePullPolicy: Never`.

Манифесты задают:

- `Deployment` с двумя репликами приложения;
- `Service` типа `ClusterIP` с HTTP-портом `8080` и gRPC-портом `9090`;
- `ConfigMap` с нечувствительными настройками `HTTP_PORT`, `GRPC_PORT` и `SHUTDOWN_TIMEOUT`;
- requests `100m` CPU и `64Mi` памяти, limits `500m` CPU и `128Mi` памяти;
- `RollingUpdate` с `maxUnavailable: 0` и `maxSurge: 1`.

Requests учитываются планировщиком при выборе узла: Pod не будет назначен на узел, которому не хватает зарезервированной CPU- и memory-ёмкости. Limits ограничивают потребление контейнера: CPU может ограничиваться по времени выполнения, а превышение memory limit может привести к перезапуску контейнера.

### Пробы здоровья

**Liveness** проверяет HTTP `GET /health`. Она отвечает на вопрос, может ли процесс обслужить HTTP-запрос; при повторных неудачах Kubernetes перезапустит контейнер.

**Readiness** проверяет стандартный gRPC health service на порту `9090`. Она подтверждает доступность gRPC-транспорта; только готовые Pod включаются в endpoints Service и получают трафик. Используется нативная gRPC-проба Kubernetes: версия кластера `v1.37.0` её поддерживает, поэтому отдельный исполняемый файл `grpc-health-probe` в образ не добавлялся. Приложение регистрирует `grpc.health.v1.Health` и выставляет статус `SERVING`.

Числовые поля Kubernetes, например `readinessProbe.grpc.port`, задаются непосредственно в манифесте и не читаются из ConfigMap. Поэтому число в пробе и порты приложения должны совпадать.

## 5. Демонстрация поведения Kubernetes

### Сценарий 1. Удаление Pod и автоматическое восстановление

Перед экспериментом Deployment содержал две готовые реплики. Один Pod был удалён командой `kubectl delete pod`. ReplicaSet заметил, что фактическое количество реплик ниже заданного, и создал замену. Новый Pod прошёл `Pending` и `ContainerCreating`, после чего перешёл в `Running` и `Ready`; в итоге Deployment снова содержит две готовые реплики.

Оставшийся готовый Pod продолжает входить в endpoints Service. Так Kubernetes восстанавливает желаемое состояние автоматически, чего один отдельно запущенный контейнер в Compose сам по себе не делает.

### Сценарий 2. Rolling update

Для обновления образ `booking-service:multi` был отмечен тегом `booking-service:v1`, затем собран образ `booking-service:v2` и загружен в Minikube. После изменения образа Deployment Kubernetes создал новые Pod, дождался их готовности и постепенно завершил старые.

В стратегии Deployment указаны `maxUnavailable: 0` и `maxSurge: 1`: во время обновления Kubernetes может временно создать дополнительную реплику, но не должен уменьшать число доступных реплик ниже заданного количества. На снимках наблюдения видны переходные состояния Pod, а команда `kubectl rollout status` завершилась сообщением `successfully rolled out`. После обновления обе реплики работают с `booking-service:v2` и имеют статус Ready.

Это показывает управляемое постепенное обновление. Отдельный непрерывный HTTP-клиент во время всего rolling update на скриншотах не записан; вывод о доступности основан на стратегии Deployment и наблюдении за Ready-репликами.

## 7. Вывод

В работе сервис из первой лабораторной работы был упакован в multi-stage Docker-образ, подготовлен для локального запуска с PostgreSQL и развёрнут в Minikube с двумя репликами. Docker Compose упрощает запуск связанных контейнеров и проверяет их здоровье, а Kubernetes дополнительно поддерживает желаемое количество Pod, исключает неготовые реплики из Service и выполняет постепенное обновление Deployment.

Бронирования пока хранятся отдельно в памяти каждого процесса. При двух репликах это означает, что состояние может различаться между Pod; для согласованной работы требуется общее постоянное хранилище. Подключение PostgreSQL подготовлено, но сохранение бронирований в БД не входит в эту работу.
